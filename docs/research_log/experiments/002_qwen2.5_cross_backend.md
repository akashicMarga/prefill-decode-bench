# 002 — Qwen2.5 1.5B Instruct: MLX vs llama.cpp

**Date:** 2026-03-15
**Hardware:** Apple M1, 16 GB unified memory, 68.25 GB/s theoretical bandwidth
**Purpose:** Fair cross-backend comparison using a standard text-only transformer

**MLX model:** `mlx-community/Qwen2.5-1.5B-Instruct-4bit` (0.87 GB)
**llama.cpp model:** `Qwen/Qwen2.5-1.5B-Instruct-GGUF` Q4_K_M (1.11 GB)

---

## Prefill

| Tokens | MLX tok/s | llama.cpp tok/s | Difference |
|--------|-----------|-----------------|------------|
| 111 | 436.7 | 451.2 | ~equal |
| 243 | 489.0 | 486.5 | ~equal |
| 485 | 490.1 | 489.6 | ~equal |
| 969 | 497.6 | 489.5 | ~equal |

Prefill performance is virtually identical across backends (within 3%).
Both are compute-bound and saturate the M1 GPU's throughput similarly.

## Decode

| KV Cache | MLX tok/s | llama.cpp tok/s | Difference |
|----------|-----------|-----------------|------------|
| 45 | 46.5 | 41.8 | MLX 11% faster |
| 243 | 47.7 | 39.1 | MLX 22% faster |
| 485 | 47.8 | 39.3 | MLX 22% faster |

MLX achieves ~15–22% better decode throughput despite lower raw bandwidth
utilization numbers.

**Bandwidth utilization:**
- MLX: 59–62% of 68.25 GB/s
- llama.cpp: 64–68% of 68.25 GB/s

## Analysis

The decode difference is a **quantization size effect**, not a framework
quality difference. MLX uniform 4-bit produces smaller weights (0.87 GB) vs
GGUF Q4_K_M mixed precision (1.11 GB). Fewer bytes per token = more tokens
per second at similar bandwidth.

llama.cpp actually achieves *higher* raw bandwidth utilization, but the larger
Q4_K_M weight file (27% bigger) means each token costs more memory traffic.
This is a quality-vs-speed tradeoff: Q4_K_M uses mixed Q4/Q5/Q6 precision for
better perplexity, at the cost of larger size.

## Findings

1. On standard text-only transformers, MLX and llama.cpp are equivalent for prefill.
2. MLX wins decode by 15–22% due to smaller uniform 4-bit weights.
3. Quantization format matters more than framework choice for decode speed.
